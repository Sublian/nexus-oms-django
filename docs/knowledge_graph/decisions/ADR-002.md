# ADR-002: Persisted Pricing — Freeze Order Prices at Creation, Never Recalculate

**Status**: ACCEPTED (2026-06-29)  
**Decision Date**: 2026-06-29  
**Context**: Order economic consistency, auditing, and reconciliation with payments & invoicing

## Problem

Every order must have a clear, immutable price history for legal and business reasons. Two approaches exist:

1. **Persisted Pricing** (chosen): Calculate price once at order creation, store in DB (subtotal, tax_amount, total_amount). Never recalculate.
2. **Dynamic Pricing**: Store only items + quantities in DB. Calculate totals on-the-fly from current Product prices.

**Question**: Which approach ensures auditable, reconcilable orders?

## Decision

**Persist prices at order creation time. Never recalculate.**

Order fields are immutable:
- `subtotal` = Σ(quantity × price_at_order)
- `tax_amount` = subtotal × (TaxConfiguration.rate / 100)
- `total_amount` = subtotal + tax_amount

Each `OrderItem.price_at_order` captures the product price at moment of sale.

### Implementation
```python
# At order creation (OrderService.create_order):
subtotal = sum(item.quantity * item.price_at_order for item in items)
tax_amount = (subtotal * tax_rate / 100).quantize(Decimal('0.01'))
total_amount = subtotal + tax_amount
order.save()  # Persisted, never touched again
```

## Reasoning

### 1. Auditing & Compliance
Orders are historical transactions. Tax authority (SUNAT) requires:
- Exact price charged on date of sale
- Exact tax calculated on that date
- Cannot change retroactively

**Dynamic approach fails**: If Product.price changes after order, reconciliation with SUNAT becomes impossible. "I issued a $100 invoice but the order shows $110 total?"

### 2. Payment Reconciliation
Payment = Order.total_amount. Must be unchanging:
- Client sees "$100" at checkout → pays $100
- Invoice shows "$100" to SUNAT
- Bank statement shows $100 received
- All three match only if Order.total_amount is frozen

### 3. Financial Reporting
Reports (SalesReport.data) store revenue snapshots:
- "Week of June 24: Revenue = $5,000"
- If order prices changed retroactively, report becomes false

### 4. Multi-Currency & Exchange Rates
Order total is in local currency at moment of sale. Future exchange rate changes do not affect the order. Persisting ensures consistency across currency migrations.

### 5. Simplicity & Performance
- No complex recalculation logic needed at query time
- No edge cases (e.g., "should I use current price or historical price?")
- Orders are queryable as-is, no dependent calculations

## Alternatives Rejected

### Alternative 1: Dynamic Pricing (Calculate on Query)
❌ **Rejected** because:
- Order.total_amount would be meaningless (why store if never used?)
- Reconciliation with payments/invoices impossible
- Tax authority would reject: "Price changed since invoice?"
- Reports become non-reproducible (same order, different totals)
- No audit trail of what price was actually charged

### Alternative 2: Store Price Separately (Order.price_snapshot JSON)
❌ **Rejected** because:
- Overcomplicates schema (two sources of truth)
- Still requires deciding which to use (price_snapshot or calculated?)
- Testing burden increases

### Alternative 3: Audit Log of Price Changes
❌ **Rejected** because:
- Still allows order total to change
- Doesn't solve reconciliation problem
- Complexity without solving core issue

## Consequences

### Positive
1. ✅ **Auditable**: Price frozen, can prove to SUNAT what was charged
2. ✅ **Reconcilable**: Payment = Invoice = Order.total (immutable)
3. ✅ **Reproducible**: Same order ID always yields same financials
4. ✅ **Compliant**: Legal requirement in most tax jurisdictions
5. ✅ **Simple**: No dynamic calculations, no edge cases

### Negative
1. ⚠️ **Price Changes Don't Affect Old Orders**: If Product.price drops tomorrow, already-paid orders don't refund. This is correct, but counterintuitive to some users.
   - **Mitigation**: Clear documentation that prices are locked at sale time
   - **Mitigation**: OrderReturn mechanism allows customer-initiated refunds if needed

2. ⚠️ **Tax Rate Changes**: If TaxConfiguration.rate changes, old orders keep old rate. Correct for past sales, but requires clear records.
   - **Mitigation**: TaxConfiguration.is_default flag ensures new rate applies only to future orders
   - **Mitigation**: Audit queries can show when rate changed

## Implementation Details

### Order Creation (OrderService.create_order)
```
For each OrderItem:
  current_price = Decimal(str(product.price))
  # price_at_order = current_price (frozen)

subtotal = sum(item.quantity * item.price_at_order)
tax_rate = order.get_tax_rate  # TaxConfiguration.rate
tax_amount = (subtotal * (tax_rate / 100)).quantize(Decimal('0.01'))
total_amount = subtotal + tax_amount

order.save()  # Immutable
```

### Tax Rate Query
```python
@property
def get_tax_rate(self):
    config = TaxConfiguration.objects.filter(
        organization=self.organization, is_default=True
    ).first()
    return config.rate if config else 18.00  # Fallback
```

### Invariants
- ✅ `order.subtotal` never changes after creation
- ✅ `order.tax_amount` never changes after creation
- ✅ `order.total_amount` never changes after creation
- ✅ `order_item.price_at_order` never changes after creation
- ✅ Product.price changes do NOT affect existing orders
