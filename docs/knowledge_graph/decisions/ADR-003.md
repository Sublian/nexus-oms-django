# ADR-003: Reactive Stock Adjustment via Django Signals, Not Synchronous Service

**Status**: ACCEPTED (2026-06-29)  
**Decision Date**: 2026-06-29  
**Context**: Inventory consistency when orders are created; automation vs explicit orchestration

## Problem

When an order is placed and OrderItem is created, stock must be decremented. Two architectural approaches exist:

1. **Reactive Signals** (chosen): Django post_save signal on OrderItem → adjust_stock_on_sale() automatically decrements Stock
2. **Explicit Service**: OrderService.create_order() calls InventoryService.decrement_stock() explicitly

**Question**: Which approach ensures robust, auditable inventory changes?

## Decision

**Use Django signals (post_save, post_create) to reactively adjust inventory.**

When OrderItem is created:
1. Django ORM fires `post_save` signal
2. `adjust_stock_on_sale()` handler executes atomically
3. Stock.quantity is decremented
4. StockMovement (Kárdex) is recorded
5. Signal result included in same transaction as OrderItem creation

### Signal Handlers
```python
@receiver(post_save, sender=OrderItem)
def adjust_stock_on_sale(sender, instance, created, **kwargs):
    if created:
        with transaction.atomic():
            stock = Stock.objects.select_for_update().filter(...).first()
            stock.quantity -= instance.quantity
            stock.save()
            StockMovement.objects.create(...)  # Audit trail
```

## Reasoning

### 1. Separation of Concerns
Business logic is in domain models, not in service orchestration:
- OrderService creates Order + Items (its job)
- Inventory adjustment is a concern of OrderItem existence
- Signal decouples inventory from order service

**Explicit service fails**: OrderService would need to know about Stock, StockMovement, Warehouse logic. Violates single responsibility.

### 2. Automatic Auditing
Signals ensure every OrderItem creation produces a StockMovement automatically:
- No code path can create OrderItem without adjusting stock
- No forgotten calls to `record_movement()`
- Audit trail is guaranteed, not optional

### 3. Testability
Signals are easier to mock/test than service chains:
- Test OrderService.create_order() independently
- Mock signal for isolated testing
- No hidden side effects in service constructor

### 4. Extensibility
Future requirements (e.g., "send SMS when stock < 10") can be added as new signal handlers:
- No modification to OrderService
- New handler just added to signals.py
- Decouples business logic from infrastructure

### 5. Transaction Safety
Signals execute within the same transaction as OrderItem.create():
- If OrderItem creation fails, Stock is never decremented
- If Stock.save() fails, entire OrderItem creation rolls back
- ACID guarantee: both succeed or both fail

## Alternatives Rejected

### Alternative 1: Synchronous Service (Explicit Orchestration)
❌ **Rejected** because:
```python
# OrderService would need:
def create_order(...):
    order = Order.objects.create(...)
    for item in items:
        oi = OrderItem.objects.create(...)
        inventory_svc.decrement_stock(oi)  # Explicit call
        inventory_svc.record_movement(oi)  # Another explicit call
```
- OrderService becomes bloated (knows too much)
- Easy to forget calls in new code paths
- Testability suffers (service has multiple concerns)

### Alternative 2: Message Queue (Async Events)
❌ **Rejected** because:
- Out-of-order processing risk (Celery task delayed)
- No ACID guarantee (OrderItem created, task fails, stock not adjusted)
- Operational complexity (need to monitor queue, retry failed messages)
- For this use case, unnecessary

### Alternative 3: Stored Procedure (Database Trigger)
❌ **Rejected** because:
- Logic hidden from Python codebase (hard to audit)
- PostgreSQL-specific (not portable)
- Harder to test locally
- No Python visibility into side effects

## Consequences

### Positive
1. ✅ **Guaranteed Audit Trail**: Every OrderItem → StockMovement, no exceptions
2. ✅ **Separation of Concerns**: OrderService only manages orders, not inventory
3. ✅ **ACID Safety**: Stock adjustment rolls back with OrderItem if transaction fails
4. ✅ **Extensible**: New handlers can hook into OrderItem creation (SMS, analytics, etc.)
5. ✅ **Testable**: Signals can be isolated from service testing

### Negative
1. ⚠️ **Implicit Behavior**: OrderService.create_order() doesn't show stock adjustment in code. Must read signal handlers.
   - **Mitigation**: Clear documentation in OrderService docstring
   - **Mitigation**: Code comments linking to signal file

2. ⚠️ **Signal Execution Order**: If multiple signals on OrderItem, order of execution is undefined.
   - **Mitigation**: Keep signals simple (no interdependencies)
   - **Mitigation**: Use @receiver decorator with dispatch_uid to prevent duplicates

3. ⚠️ **Debugging Complexity**: Stack traces may not show OrderService → Signal clearly.
   - **Mitigation**: Logging in signal handler shows audit trail
   - **Mitigation**: Django debug toolbar shows signal execution

## Implementation Details

### Signals File (src/domain/signals.py)
```python
@receiver(post_save, sender=OrderItem)
def adjust_stock_on_sale(sender, instance, created, **kwargs):
    if created:
        with transaction.atomic():
            stock = Stock.objects.select_for_update().filter(
                product=instance.product,
                organization=instance.organization
            ).first()
            
            if stock:
                stock.quantity -= instance.quantity
                stock.save()
                
                StockMovement.objects.create(
                    organization=instance.organization,
                    stock=stock,
                    quantity=instance.quantity,
                    movement_type=StockMovement.MovementType.OUTPUT,
                    reason=f"Venta: Pedido #{instance.order.id}",
                    order=instance.order
                )
```

### Invariants
- ✅ Signal only fires if `created=True` (prevents re-triggering on updates)
- ✅ select_for_update() prevents race conditions
- ✅ StockMovement created atomically with Stock update
- ✅ No code path can create OrderItem without signal execution
