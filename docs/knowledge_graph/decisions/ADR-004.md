# ADR-004: Asynchronous Invoice Synchronization via Polling, Not Webhooks

**Status**: ACCEPTED (2026-06-29)  
**Decision Date**: 2026-06-29  
**Context**: Invoice status reconciliation with SUNAT through Nubefact provider; reliability, operational simplicity, audit trail

## Problem

After submitting an invoice to Nubefact, we must learn SUNAT's decision (accepted/rejected/observed). Two patterns exist:

1. **Polling** (chosen): Celery Beat triggers periodic tasks that query Nubefact "What did SUNAT say?" every 1 minute with exponential backoff.
2. **Webhooks**: Nubefact sends HTTP POST to our endpoint when SUNAT decides.

**Question**: Which ensures reliable invoice reconciliation with minimal operational burden?

## Decision

**Poll Nubefact asynchronously. Never rely on webhooks.**

Flow:
1. Invoice submitted to Nubefact (síncrono)
2. InvoiceSyncQueue(STATUS_PENDING, next_retry_at=now) created
3. Celery Beat runs `sync_pending_invoices_task` every 1 minute
4. Task fetches all due entries, dispatches `sync_single_invoice_task` for each
5. Each task queries Nubefact, parses response, updates Order.invoice_status
6. Backoff exponential if still pending: 60s → 5m → 15m → 30m → 1h → 6h → 24h
7. Max 7 attempts (MAX_ATTEMPTS), then mark exhausted for manual review

### Implementation
```python
# Periodic scheduler
@shared_task
def sync_pending_invoices_task():
    entries = InvoiceSyncQueue.all_objects.filter(
        status=STATUS_PENDING,
        next_retry_at__lte=now()
    )
    for entry in entries:
        sync_single_invoice_task.delay(entry.id)

# Per-entry sync
@shared_task
def sync_single_invoice_task(entry_id):
    with transaction.atomic():
        entry = InvoiceSyncQueue.all_objects.select_for_update().get(id=entry_id)
        # ... lock check, idempotency ...
        result = InvoiceStatusQueryUseCase().execute(entry)
        # ... update order.invoice_status, entry.status ...
```

## Reasoning

### 1. Webhook Delivery Unreliability
Webhooks depend on:
- Nubefact's outbound network (may fail, timeout, rate limit)
- Our endpoint availability (deployment, crashes)
- Retry policy (does Nubefact retry on 5xx?)
- Out-of-order delivery (Nubefact sends #2 before #1)

**If webhook fails**: Invoice status unknown forever. No automatic recovery.

Polling eliminates all of these: We control retry timing and count.

### 2. Audit Trail & Idempotency
Polling stores every attempt (InvoiceSyncQueue.last_attempt_at, .attempts):
- Audit trail: "We checked SUNAT 7 times, last on June 29 at 14:30"
- Idempotency: `select_for_update()` prevents duplicate polls from concurrent workers
- Lock state (locked_at) prevents double-processing between Celery workers

Webhooks are fire-and-forget: If we process twice, we don't know it. If we miss one, no record.

### 3. Operational Simplicity
Polling requires:
- Celery Beat (already required for other jobs: daily reports, exchange rates)
- InvoiceSyncQueue table (simple, persistent)
- No firewall rules or IP whitelisting (we initiate, not them)

Webhooks require:
- Public HTTP endpoint exposed to internet
- IP whitelisting (which Nubefact IPs to trust?)
- Secret signing (HMAC validation)
- Error handling (retry on 5xx? How many times?)
- Testing (need to mock Nubefact webhook sender)

### 4. Decoupling from Provider
Polling works even if Nubefact's webhook system fails:
- We don't wait for their delivery
- We don't depend on their retry logic
- We can change providers (APIMigo, another) without changing architecture

Webhooks couple us to Nubefact's reliability.

### 5. No Out-of-Order Risks
Polling processes entries in order by `next_retry_at`:
- Entry A (created 12:00) processes before Entry B (created 12:01)
- Audit is chronological

Webhooks can arrive out-of-order if Nubefact has network hiccups.

## Alternatives Rejected

### Alternative 1: Webhooks (Push Model)
❌ **Rejected** because:
- Nubefact delivery may fail, no fallback
- Audit trail is implicit (must store webhook in db, not automatic)
- Requires public endpoint (security surface area)
- Out-of-order delivery possible
- No control over retry behavior
- Testing complexity (mock HTTP sender)

### Alternative 2: Webhook + Polling (Hybrid)
❌ **Rejected** because:
- Complexity without clear benefit (two notification channels)
- Still must handle webhook failures
- Still must poll as fallback (then why webhook at all?)
- Harder to debug (two code paths for same outcome)

### Alternative 3: Synchronous Wait in submit_invoice_task
❌ **Rejected** because:
- SUNAT can take minutes to decide
- Task would block, preventing concurrency
- Timeout risk (task killed by Celery after 30m)
- User would see "Submitting..." spinner for 10+ minutes

## Consequences

### Positive
1. ✅ **Reliable**: No external notification dependency. We control retry timing.
2. ✅ **Auditable**: Full history in InvoiceSyncQueue (all attempts, timestamps, responses).
3. ✅ **Idempotent**: select_for_update() + status checks prevent double processing.
4. ✅ **Operational Simplicity**: No webhooks, firewalls, IP whitelists.
5. ✅ **Decoupled**: Invoice logic independent of Nubefact's webhook reliability.
6. ✅ **Backoff Built-In**: Exponential delays avoid hammering SUNAT with repeated queries.

### Negative
1. ⚠️ **Latency**: Status not real-time. SUNAT decides at 12:05, we learn at 12:06 (1 min delay).
   - **Mitigation**: For end users, this is acceptable (invoice decision is not instantaneous anyway)
   - **Mitigation**: If urgent, can manually query via dashboard

2. ⚠️ **Celery Dependency**: Polling depends on Celery Beat scheduler running.
   - **Mitigation**: Monitor Celery Beat heartbeat
   - **Mitigation**: Alert if sync_pending_invoices_task hasn't run in > 2 minutes

3. ⚠️ **Database Churn**: InvoiceSyncQueue grows with each attempt (one row per submission).
   - **Mitigation**: Archive old entries after 90 days
   - **Mitigation**: Index on (status, next_retry_at) for efficient queries

## Implementation Details

### InvoiceSyncQueue States
```
PENDING        → attempt <= MAX_ATTEMPTS, retry pending
               ↓
PROCESSING     → worker acquired lock, polling SUNAT
               ↓
COMPLETED      → SUNAT gave final answer (accepted/rejected/observed)
               ↓ (alternate paths)
FAILED         → Permanent error from Nubefact (4xx, no config, no external_id)
EXHAUSTED      → MAX_ATTEMPTS reached without terminal answer
DEAD_LETTER    → Manual intervention required
```

### Backoff Schedule
```
Attempt 1: 60s
Attempt 2: 5m
Attempt 3: 15m
Attempt 4: 30m
Attempt 5: 1h
Attempt 6: 6h
Attempt 7: 24h (max)
```

### Invariants
- ✅ Only STATUS_PENDING entries are polled
- ✅ Only entries where next_retry_at <= now() are dispatched
- ✅ select_for_update() ensures one worker per entry
- ✅ Failed or exhausted entries do not re-poll
- ✅ Stale locks (locked_at > 10 min) are reprocessed
