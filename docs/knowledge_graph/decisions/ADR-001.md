# ADR-001: Why Application Guards BEFORE PostgreSQL RLS

**Status**: ACCEPTED (2026-06-27)
**Decision Date**: 2026-06-14
**Context**: S1 Tenant Isolation Hardening vs S2 PostgreSQL RLS

## Problem

Nexus OMS multi-tenant system requires defense-in-depth against data leakage between organizations. Two primary approaches exist:

1. **Application-level guards** (S1): TenantManager + TenantViewMixin + middleware
2. **Database-level isolation** (S2): PostgreSQL Row-Level Security (RLS) policies

**Question**: Which should execute first?

## Decision

**Execute S1 (Application Guards) BEFORE S2 (PostgreSQL RLS).**

### Timeline
- ✅ **S1 Completed**: 2026-06-14 (337 tests passing)
- 🔄 **S2 Starting**: 2026-06-27 (Knowledge Graph + RLS design)

## Reasoning

### 1. Faster Time-to-Secure
Application guards are deployed via code + test, no DB downtime:
- No DDL (CREATE POLICY requires schema changes + migration)
- No production window-of-risk during RLS deployment
- Rollback simple: git revert + redeploy

**vs RLS**:
- Requires careful DDL planning (ALTER TABLE ... ENABLE ROW LEVEL SECURITY)
- Migration risk: RLS on wrong table = data inaccessible
- Testing complexity: must simulate pg_superuser bypass scenarios

### 2. Layered Defense Principle
Application + Database guards > Database guards alone:

```
Request → Middleware (S1)
        ├─ validate X-Org-ID
        ├─ set thread-local context
        └─ TenantManager filters queryset (S1)
              ↓
        → PostgreSQL receives filtered data
        → RLS policy double-checks (S2)
        → Only rows matching organization pass
```

If application filter is bypassed (bug in middleware), RLS catches it.
If RLS is misconfigured, application filter still protects.

### 3. Testing Coverage
S1 proof via pytest is faster than S2 testing:
- Application guards: 337 tests exercising all ViewSets + code paths
- RLS policies: requires `SET session authorization` + concurrent connections to test

S1 achieved **337 passing tests** with high confidence.
S2 will add RLS, but application guardrails already proven.

### 4. Early Feedback Loop
S1 deployment (2026-06-14) gave 2 weeks of:
- Real traffic through TenantManager filters
- Integration testing in staging
- Zero data leakage incidents
- Confidence in application isolation

Deploy S2 (RLS) now while application layer is proven stable.

## Alternatives Rejected

### Alternative 1: RLS First
❌ **Rejected** because:
- Requires downtime for migration
- RLS is "invisible" (no code audit trail in Python)
- Harder to test locally (requires full PostgreSQL + pg_stat_statements)
- Higher rollback risk if misconfigured

### Alternative 2: Parallel (S1 + S2 Simultaneously)
❌ **Rejected** because:
- Double dev effort (application + RLS design concurrent)
- Harder to isolate root cause if issue occurs (app or DB?)
- Context-switching overhead

## Consequences

### Positive
1. ✅ Time-to-market: Live isolation 2 weeks earlier
2. ✅ Confidence: 337 tests prove application isolation works
3. ✅ Layered defense: S2 now adds DB-level guarantee
4. ✅ Rollback safety: S1 alone is safe; S2 failure doesn't breach S1

### Negative
1. ⚠️ Until S2 deployed (June 2026): RLS gap exists
   - Mitigation: pg_superuser access restricted to DBA role only
   - Mitigation: No direct SQL queries in application code
   - Mitigation: Regular audit of pg_roles + permissions

2. ⚠️ S2 deployment adds complexity
   - Mitigation: RLS policies written + tested before migration
   - Mitigation: Canary deploy to staging first
