# ADR-005: Payment Service as Tenant-Self-Contained, Transition-Guarded

**Status**: ACCEPTED (2026-08-09)
**Decision Date**: 2026-08-09
**Context**: Registration of pending payments (TRANSFER/WALLET) + Celery sync confirmation; found during adversarial review that the payment flow depended on ambient tenant context and on unconditional order mutations.

## Problem

The payment pipeline (PaymentService + `sync_single_payment_task`) had four defects:

1. **F1 — Tenant context leak in async confirmation (CRITICAL).** The Celery worker runs in a process with **no** tenant context. `sync_single_payment_task` correctly bypasses `TenantManager` via `Payment.all_objects`, but then calls `confirm_payment` → `_mark_order_paid` → `OrderWorkflowService._claim_workflow_lock`, which uses `Order.objects` (TenantManager). With no context, TenantManager returns `.none()` → `DoesNotExist` → the `@transaction.atomic` in `confirm_payment` rolls back → the payment stays `pending` and is retried every 60s **forever**. The unit test passed only because eager Celery ran in the same thread where the test fixture had set the context.

2. **F2 — Approved payment revives a cancelled order (HIGH).** A payment can enter `pending` (TRANSFER/WALLET) and the order can be cancelled (`PENDING→CANCELLED`, stock already restored). When the transfer later clears, `_apply_result` set `order.status = PAID` **unconditionally**, reviving a cancelled order and creating cobro+inventario inconsistency.

3. **F3 — Concurrent `/pay/` race (MEDIUM-HIGH).** The duplicate check (`Payment.objects.filter(order=...).first()`) is in-memory, not DB-serialized. Two simultaneous POSTs both pass the check, both create a Payment, and the `OneToOneField` raises `IntegrityError` → 500.

4. **F4 — Historical `fee_amount=0` (MEDIUM).** Migration 0018 backfilled `status`/`approved_at`/`fee_rate` but not `fee_amount`, leaving pre-PaymentService approved payments with `fee_amount=0` → finance reports computed `net_amount = amount` (fee not deducted).

## Decision

### D1. `PaymentService` owns its tenant context (F1)

`process_payment` and `confirm_payment` wrap their bodies in `TenantContextManager(order.organization_id)`, regardless of where they are called (HTTP middleware, Celery worker, scripts).

- Contract: **a service method that mutates tenant data must never rely on ambient context.** The task should not need to set context — the service is self-contained.
- `Payment.all_objects` remains the *entry point* for the worker (finding rows across tenants); the *business logic* gets an explicit context.

### D2. Order promotion to PAID is transition-guarded (F2)

`_mark_order_paid` only flips `order.status = PAID` when `PAID ∈ VALID_TRANSITIONS[order.status]`.

- Otherwise it logs an `ANOMALY` and leaves the order untouched. The payment **does** become `approved` (the gateway charged); the anomaly is the honest record.
- Side benefit: double confirmation (manual + task race) hits `PAID ∉ VALID_TRANSITIONS[PAID]` → workflow runs exactly once.
- API `confirm-payment` now reports the real outcome ("La orden pasó a PAID" vs "Pago confirmado, pero la orden no cambió de estado").
- **Deferred**: a future PaymentAnomaly model to track these cases operationally (see Limitations).

### D3. Serialize payments per order with a row lock (F3)

`process_payment` re-fetches the order with `Order.objects.select_for_update()` inside the atomic block, then re-runs the duplicate check.

- The caller's in-memory `order` object is re-synced via `refresh_from_db()` so views/renderers see the final status.
- `select_for_update` requires Postgres (a no-op on SQLite) — acceptable, the stack is Postgres-only.

### D4. Backfill migration for `fee_amount` (F4)

New migration `0019_backfill_fee_amount`: recomputes `fee_amount = amount * fee_rate / 100` (ROUND_HALF_UP) for `status='approved', fee_rate>0, fee_amount=0`.

- Uses `Payment._base_manager` (plain, unfiltered) — **not** `all_objects`: historical models in migrations only preserve the default manager (TenantManager), and `all_objects` is a custom manager not carried into model state. This is the same trap that made 0018's `Payment.objects.all()` a silent no-op when run without tenant context.
- Applied to dev DB: 13 approved payments corrected (e.g. 1605.98 × 3.5% → 56.21).

### D5. Money rounding uses ROUND_HALF_UP (F5)

Commission quantize now passes `rounding=ROUND_HALF_UP` instead of the default `ROUND_HALF_EVEN` (banker's rounding) — edge cases like 0.005 should round up for money.

## Reasoning

- **D1**: The fail-safe `TenantManager` (returns `.none()` without context) is a *crash-safety* feature, not a *call-site* contract. Async tasks are a first-class caller; the service must be context-agnostic.
- **D2**: State-machine invariants (declared in `VALID_TRANSITIONS`) are the single source of truth. No code path may set `PAID` bypassing them.
- **D3**: Application-level locks (in-memory flag) don't work across Celery workers/processes. The DB row lock is the only correct serialization primitive here.
- **D4**: Backfills must never depend on `TenantManager`; historical model state differs from live models.
- **D5**: `Decimal.quantize` default rounding is documented as ROUND_HALF_EVEN; money conventions favor HALF_UP.

## Alternatives Rejected

- **Task sets the context itself** (in `sync_single_payment_task`): rejected — fixes one caller, leaves scripts/management commands exposed. The service is the correct single place.
- **Payment anomaly = reject the payment**: rejected — the gateway already moved money; rejecting/keeping `pending` would either lose the record or retry forever.
- **Distributed lock (Redis) for F3**: rejected — over-engineering; a Postgres row lock on the order already serializes correctly and is transaction-aligned.
- **Only backfill via ORM command**: rejected — data migrations should be codified as migrations so every environment (incl. prod) applies the same correction.

## Consequences

### Positive
1. ✅ Async confirmation works from the worker process (no ambient context).
2. ✅ Cancelled orders are never revived; double-confirm is idempotent end-to-end.
3. ✅ Concurrent payments are serialized per order (409 on second, not 500).
4. ✅ Historical finance figures now reflect the fee deduction.
5. ✅ 6 new regression tests; suite green (393 passed).

### Negative / Documented limitations (not fixed in this ADR)
1. ⚠️ **Declined history is deleted on retry** (`existing.delete()`): OneToOne design; a declined payment is replaced by the new attempt. No audit trail of declined attempts.
   - **Mitigation**: log lines; future PaymentAttemptLog table if needed.
2. ⚠️ **Provider HTTP call inside the DB transaction** (process/confirm): a slow provider holds the row lock. Acceptable for the mock/Phase A; for the Izipay phase, restructure to commit-then-confirm.
3. ⚠️ **Anomalies (D2) are log-only**: no operational queue. When Izipay goes live, add PaymentAnomaly model + dashboard widget.
4. ⚠️ **API returns `float`** for money fields (fee_amount, net_amount): JSON convenience; keep Decimal in the DB.
5. ⚠️ **Eager invoice task inside confirm**: `create_invoice_task.delay` is eager in tests; on invoice failure the whole confirm rolls back (payment stays pending) — self-heals via the 60s beat.
6. ⚠️ **`get_payment_provider('izipay')` raises NotImplementedError → 500**: expected until the Izipay provider exists; should map to 501 (PaymentServiceError) when implemented.
