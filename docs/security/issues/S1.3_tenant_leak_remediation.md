```python
class TenantModel(models.Model):
    organization = models.ForeignKey(
        'domain.Organization',
        on_delete=models.CASCADE,
        related_name="%(class)s_items"
    )

    # Automatic filtering manager (respects context, fail-safe empty if no context)
    objects = TenantManager.from_queryset(TenantQuerySet)()

    # Unfiltered access for admin/audit (bypass tenant filtering)
    unfiltered = models.Manager()
    # Backward compatibility alias
    all_objects = models.Manager()

    class Meta:
        abstract = True
```

**Análisis**:
- ✅ `.objects` = TenantManager (auto-filters por contexto)
- ✅ `.unfiltered` = Manager() (bypass explícito)
- ⚠️ `.all_objects` = Manager() (backward compat, permite bypass)

**Síntoma**: ViewSets usan `.all_objects` para bypass sin penalización.

## Escenario de Explotación Confirmado

### Attack Vector

```
1. Superuser obtiene token JWT (claims incluyen organization_id pero ignorado)
2. GET /api/v1/products/ sin header X-Org-ID
3. TenantViewMixin.get_organization() retorna None (no header)
4. ProductViewSet.get_queryset() ejecuta: Product.all_objects.all()
5. Retorna ALL productos de ALL tenants (no solo de la org del user)
```

| Endpoint | Datos Sensibles | Escala |
|----------|-----------------|--------|
| `/api/v1/products/` | Precios, SKU, inventario total | 100s de productos cross-tenant |
| `/api/v1/orders/` | Nombres clientes, emails, direcciones, montos | 1000s de órdenes cross-tenant |
| `/api/v1/reports/` | Total ventas, volumen, datos financieros JSON | Resumenes financieros globales |

## Mecanismo de Defensa (Post S1B)

**TenantManager (S1B)** debería:
1. Filtrar automáticamente si `.objects` es usado ✓
2. Retornar empty si contexto está missing ✓
3. Pero ViewSets usan `.all_objects` (intencional bypass) ❌

**Síntesis**: El problema es que `.all_objects` existe para bypass legítimo (admin/audit), pero ViewSets lo usan sin guarda de contexto.

## Evidencia de Centralización de Flujo (S1C Final Audit)

### TenantViewMixin Código Completo

**Archivo**: `src/interfaces/api/views.py:34-44`

```python
class TenantViewMixin:
    """
    Resuelve la organización activa desde el usuario autenticado.
    Superusuarios pueden apuntar a cualquier org via X-Org-ID header.
    """
    def get_organization(self):
        user = self.request.user
        if user.is_superuser:
            org_id = self.request.META.get('HTTP_X_ORG_ID')
            return get_object_or_404(Organization, id=org_id) if org_id else None
        return user.organization
```

**Análisis**:
- ✅ Centralized en UNA clase (no duplicado)
- ❌ No hay guard para X-Org-ID faltante en superuser
- ❌ Retorna None si superuser sin header

## Respuestas a 3 Preguntas de Control

### 1. ¿Bypass centralizado o duplicado?

**CENTRALIZADO EN MIXIN** ✅

```
TenantViewMixin.get_organization()
    └── return None if superuser sin X-Org-ID
        └── Inherited by ALL 4 ViewSets
            └── Each ViewSet duplicates ternario pattern
                └── Calls .all_objects.all() if None
```

**Veredicto**: Problema no está en Mixin, está en que **CADA ViewSet replica el patrón inseguro**.

El Mixin es CORRECTO (centralizado). El leak es DUPLICADO (patrón ternario en 4 lugares).
